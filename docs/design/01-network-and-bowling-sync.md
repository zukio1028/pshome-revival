# ネットワーク基盤とボーリング同期方式の選定（MVP）

**決定（2026-10-16）**：Fusion 2 Shared Mode / ハイブリッド同期 / ラウンジ内レーン・観戦可・1レーン最大4人

前提：個人開発 / Unity（C#）/ iOS・Android / MVP = 単一パブリックラウンジ（アバター移動＋チャット）＋ボーリング

> 料金・無料枠は改定が多いため、契約前に各公式の最新プランを必ず確認してください（本書の金額感は目安）。

---

## 1. ネットワーク基盤の比較

| 観点 | **Photon Fusion 2（Shared Mode）** | Photon Quantum 3 | Unity NGO + UGS（Relay / Lobby / Distributed Authority） | Mirror（または FishNet）＋自前ホスティング |
|---|---|---|---|---|
| 実装コスト | ◎ 低。Shared Mode は「各クライアントが自分の所有物を権威として持つ」ためサーバー実装不要 | △ 高。決定論ECS・専用の書き方（Unity の MonoBehaviour 流儀が使えない） | ○ 中。NGO 2.x の Distributed Authority で Fusion Shared に近い構成が可能。Relay/Lobby/Vivox 等の組み合わせ設定が必要 | △ 中〜高。ネットコードは無料だが、サーバービルド・ホスティング・スケーリングを自分で持つ |
| 運用コスト | ◎ サーバー管理不要。無料枠（開発用の小規模 CCU）→ 有料は CCU 課金 | ○ Photon クラウド上で動く。料金体系は要確認 | ○ 従量課金（無料枠あり）。サーバー管理は不要 | × 常時稼働の専用サーバー代＋運用工数（Edgegap 等を使っても設定は自分） |
| ラウンジ（多人数移動・チャット）適性 | ◎ 補間・関心領域（AoI）・ホストマイグレーション不要 | ○ 可能だがラウンジにはオーバースペック | ○ 可能。DA はまだ比較的新しく事例が少なめ | ○ 可能（サーバー権威で堅牢） |
| ボーリング物理適性 | ○ 投げた人が権威。結果確定を一人に寄せる設計と相性良 | ◎ 決定論物理で全員が完全一致 | ○ Fusion と同様の設計 | ◎ サーバーで物理を回せば完全一致（ただしサーバー費） |
| モバイル実績・情報量 | ◎ 日本語情報・サンプル（Fusion のサンプル群）が豊富 | ○ 格ゲー・対戦系の実績多 | ○ 公式ドキュメント充実、DA は情報少なめ | ○ コミュニティ大きいがモバイル運用は自力 |
| ベンダーロックイン | △ Photon 依存 | △ Photon 依存（さらに強い） | △ Unity 依存 | ◎ なし |

### 推奨：**Photon Fusion 2 / Shared Mode**
- 個人開発で「サーバーを書かない・持たない」が最大の工数削減。Shared Mode はアバター移動（各自が自分の位置の権威）とボーリング（投げた人が権威）の両方に素直にハマる。
- チャットは MVP では **Fusion の RPC（ルーム内チャット）** で十分。ルームを跨ぐ全体チャットや DM が必要になったら Photon Chat を追加。
- 次点：Unity 一本化したい場合は **NGO 2.x + Distributed Authority**。Quantum は「ボーリングでガチ対戦・ランキングの公正性が最重要」になった時点で再検討。
- Mirror/FishNet は「将来の運用費を最小化したい」「ロックインを絶対避けたい」場合のみ。MVP では工数増が大きい。

### Fusion 2 前提でのルーム設計（案）
- 1ラウンジ = 1 Fusion セッション（例：最大 20〜30 人）。満員なら自動で別インスタンス（「ラウンジ2」）に振り分け。
- ボーリングレーンはラウンジ内の空間オブジェクトとして同じセッション内に置く（観戦できるのが PS Home 的な楽しさ）。
- アバター：`NetworkTransform` ＋ アニメーションパラメータ同期。アバター素材は 02 で選定。

## 2. ボーリングの物理演算同期方式の比較

| 観点 | A. 完全リアルタイム剛体同期 | B. 投球パラメータのみ送信 → 各端末で再現 | **C. ハイブリッド（推奨）** | D. 決定論物理（Quantum 等） |
|---|---|---|---|---|
| 概要 | ボール＋ピン10本の位置/回転を毎tick送信 | 力・角度・スピン・開始位置だけ送り、各自 PhysX で再生 | 投げた人（権威）がローカル物理で結果を確定。他者には投球パラメータで即時再生し、最後に「倒れたピン＋最終姿勢」を送って補正 | 全端末で同一入力→同一結果を保証 |
| 帯域 | × 多い（11剛体×tick） | ◎ ほぼゼロ | ◎ 少ない（開始時＋終了時のみ） | ◎ 入力のみ |
| 見た目の滑らかさ | △ 遅延・ジッターで補間が必要、ピン衝突が不自然になりがち | ◎ ローカル物理なので滑らか | ◎ ローカル物理で滑らか | ◎ |
| 結果の一致 | ◎ | × **一致しない**。PhysX は端末・CPU間で決定論ではなく、ピン倒れ方が端末ごとに変わる → スコアがズレる | ○ スコアは権威の結果に一本化。観戦者側の見た目が最後に少し補正されるだけ | ◎ |
| 実装コスト | △ 中〜高 | ◎ 最小 | ○ 低〜中（Bに「結果確定と補正」を足すだけ） | × 高 |
| チート耐性 | ○ | △ | △ 投げた人の端末が結果を決める（MVPでは許容、ランキング導入時に再検討） | ◎ |

### 推奨：**C. ハイブリッド**
1. 投球者がスワイプ入力 → 投球パラメータを RPC で全員へ送信（同時に自分の端末で物理開始）。
2. 観戦者は受信したパラメータで自分の端末でもローカル再生（滑らか・即時）。
3. 投球者の端末で全ピン静止後、「倒れたピンのビットマスク＋各ピンの最終位置/回転」を Networked プロパティで送信。
4. 観戦者は自分の再生結果と違うピンだけ、短い補間で最終姿勢へ寄せる。**スコアは常に投球者の確定結果を使用**。

実装上のコツ
- `Time.fixedDeltaTime` と Solver Iterations を固定し、ピンの質量・摩擦・反発をプリセット化 → B単体でも一致率が上がり、補正が目立たなくなる。
- スピン（フック）は物理任せにせず「横方向の力を時間で加える」自前カーブにすると再現性と気持ちよさが両立しやすい。
- 投球者が途中で切断した場合は、そのフレームを「やり直し」扱いにするのが MVP では最も安い。

## 3. 判断してほしいこと（推奨付き）

1. **ネット基盤**：Photon Fusion 2 Shared Mode（推奨）／ Unity NGO + Distributed Authority ／ Photon Quantum
2. **ボーリング同期**：C. ハイブリッド（推奨）／ B. パラメータのみ（最小工数・スコアずれ許容）／ D. 決定論
3. **ボーリングの遊び方**：ラウンジ内のレーンで観戦可・1レーン最大4人（推奨）／ ボーリングは別ルームに移動して遊ぶ ／ 1人プレイ＋スコア共有のみ

この3点が決まったら、次のステップとして「Unity プロジェクト初期構成（バージョン、URP、使用アセット一覧、フォルダ構成）」と「最小ラウンジ（接続→アバター移動→チャット）」の実装手順に進みます。
